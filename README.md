# Oracle Performance Patterns

Практическая лаборатория по **производительности, масштабированию и надёжности Oracle Database**.

Этот репозиторий помогает разобраться, как проектировать Oracle-системы, которые должны работать с большими объёмами данных и высокой нагрузкой.

Здесь собраны не только описания технологий, а **рабочие SQL и PL/SQL-примеры**, которые можно изучать, запускать, изменять и использовать как основу для собственных проектов.

---

## 🎯 Что вы получите от проекта

Репозиторий будет полезен, если вы:

* оптимизируете медленные запросы Oracle;
* работаете с таблицами на миллионах строк;
* проектируете высоконагруженные системы;
* хотите понять, когда использовать разные типы индексов;
* изучаете Partitioning и Partition Pruning;
* хотите уменьшить количество SQL ↔ PL/SQL переключений;
* проектируете аудит и защиту данных на уровне БД;
* готовитесь к техническому интервью по Oracle;
* ищете практические примеры вместо теоретического описания Oracle-функций.

Главная ценность проекта — возможность увидеть **не только синтаксис технологии, но и задачу, которую она решает**.

# 🚀 Какие задачи можно решать

## 1. Ускорить работу больших таблиц

При росте таблицы обычный запрос может начинать обрабатывать слишком большой объём данных.

В проекте показано горизонтальное секционирование таблицы `orders_hist` по годам.

```sql
PARTITION BY RANGE (order_date)
```

Это позволяет Oracle использовать **Partition Pruning** и не читать секции, которые не относятся к запросу.

### Что это даёт

* меньше данных обрабатывается при запросе;
* проще работать с историческими данными;
* удобнее обслуживать большие таблицы;
* появляется основа для масштабирования таблиц с большим объёмом данных.

---

# ⚡ 2. Понять, когда помогает Index Skip Scan

В проекте используется составной индекс:

```sql
(status, order_date)
```

При определённых условиях Oracle способен использовать такой индекс даже тогда, когда первая колонка индекса отсутствует в условии запроса.

Это позволяет на практике изучить механизм **Index Skip Scan** и понять, почему один и тот же индекс может вести себя по-разному в зависимости от данных и запроса.

### Что можно получить

* понимание поведения составных индексов;
* практический пример Skip Scan;
* основу для анализа плана выполнения;
* понимание того, когда дополнительный индекс действительно необходим, а когда Oracle может использовать существующий.

> Важно: Skip Scan не является универсальной заменой правильно спроектированным индексам. Его эффективность зависит от структуры данных, кардинальности и конкретного запроса.

# 🔄 3. Уменьшить конкуренцию при массовых INSERT

Для некоторых сценариев в проекте используются **Reverse Key Indexes**.

Они позволяют изменить распределение индексных ключей и снизить вероятность концентрации параллельных операций в одних и тех же блоках.

### Что это помогает изучить

* проблему Hot Blocks;
* особенности индексирования последовательных ключей;
* влияние структуры индекса на конкурентную запись;
* ситуации, в которых Reverse Key Index может быть полезен.

---

# 🧠 4. Сократить лишнюю работу при повторных вычислениях

В проекте рассматриваются:

* Global Temporary Tables;
* Oracle Result Cache.

### GTT

Global Temporary Table позволяет хранить промежуточные данные отдельно для пользовательской сессии или транзакции.

Это удобно для сценариев, где нужно:

* собрать промежуточный набор данных;
* выполнить несколько операций над ним;
* не создавать постоянную таблицу;
* изолировать временные данные между сессиями.

### Result Cache

Result Cache позволяет повторно использовать результаты подходящих функций и запросов вместо выполнения одной и той же работы заново.

### Практический результат

Проект помогает понять, **когда кэширование действительно может уменьшить повторные вычисления**, а когда оно не подходит.

# 📦 5. Обрабатывать большие объёмы данных через PL/SQL эффективнее

Пакет:

```text
pkg_orders
```

демонстрирует пакетную обработку с использованием:

```sql
BULK COLLECT
FORALL
```

Вместо обработки каждой строки отдельным переключением между SQL и PL/SQL можно работать с данными пакетами.

### Что это даёт

* меньше переключений SQL ↔ PL/SQL;
* более эффективная массовая обработка;
* понимание Bulk Processing;
* практическая основа для оптимизации PL/SQL-кода.

Это особенно полезно при обработке больших наборов данных.

---

# 🧾 6. Сохранять аудит даже при откате основной транзакции

В проекте используется **Autonomous Transaction** для записи событий.

Процедура:

```text
log_event
```

может фиксировать информацию независимо от основной транзакции.

Например:

```text
Основная операция
      │
      ├── ошибка
      │
      └── ROLLBACK
             │
             └── запись события остаётся
```

### Что можно изучить

* автономные транзакции;
* аудит ошибок;
* независимое журналирование;
* проектирование диагностических механизмов внутри БД.

# 🛡️ 7. Контролировать некорректные изменения данных

Проект содержит серверную бизнес-валидацию через триггеры.

Например, `trg_product_price_audit.sql` демонстрирует проверку изменения цены.

Это позволяет перенести критические ограничения с приложения непосредственно в базу данных.

### Зачем это нужно

Если несколько приложений используют одну БД, бизнес-правило, критичное для целостности данных, не должно зависеть только от одного frontend/backend-сервиса.

Oracle может выступать дополнительным уровнем защиты.

---

# 🔐 8. Ограничивать доступ к данным на уровне строк

Проект показывает использование:

**VPD — Virtual Private Database.**

Идея:

```text
Пользователь A → видит свои данные
Пользователь B → видит свои данные
Администратор → получает другой уровень доступа
```

Фильтрация выполняется на уровне базы данных.

### Что это даёт

* изучение row-level security;
* централизованное управление доступом;
* уменьшение зависимости безопасности от клиентского приложения;
* практический пример VPD.

---

# 🎭 9. Скрывать чувствительные данные

Проект содержит пример маскирования данных.

Например:

```text
ivan@example.com
      ↓
i***@example.com
```

Это позволяет изучить подходы к отображению чувствительных данных без необходимости показывать их полностью.

---

# ♻️ 10. Сохранять историю вместо физического удаления

Вместо:

```sql
DELETE FROM orders;
```

может использоваться логическое удаление:

```sql
UPDATE orders
SET status = 'DELETED';
```

Такой подход позволяет сохранить запись и историю изменений.

### Что это даёт

* возможность восстановления;
* сохранение истории;
* аудит операций;
* более предсказуемую работу связанных данных.

При этом soft delete имеет свои издержки и должен проектироваться с учётом индексов, запросов и объёма таблицы.

# 🔬 Как изучать проект эффективнее

Не стоит воспринимать репозиторий просто как коллекцию SQL-файлов.

Для каждой технологии полезно пройти цикл:

```text
Проблема
   ↓
Базовая реализация
   ↓
Oracle-механизм
   ↓
План выполнения / поведение
   ↓
Оптимизированный вариант
   ↓
Сравнение результата
```

Например:

```text
Большая таблица
      ↓
Partitioning
      ↓
Partition Pruning
      ↓
Меньше обрабатываемых секций
```

Так становится понятно не только **как работает технология**, но и **зачем она нужна**.

# 📈 Главная идея проекта

Этот репозиторий не пытается показать как можно больше возможностей Oracle.

Его задача — показать **как возможности Oracle помогают решать конкретные инженерные проблемы**:

| Проблема                       | Инструмент             |
| ------------------------------ | ---------------------- |
| Большой объём данных           | Partitioning           |
| Чтение нужных секций           | Partition Pruning      |
| Особенности составных индексов | Index Skip Scan        |
| Конкурентная запись            | Reverse Key Index      |
| Временные данные               | GTT                    |
| Повторные вычисления           | Result Cache           |
| Массовая обработка             | BULK COLLECT / FORALL  |
| Независимый аудит              | Autonomous Transaction |
| Контроль бизнес-правил         | Database Triggers      |
| Ограничение доступа            | VPD                    |
| Скрытие данных                 | Data Masking           |
| Сохранение удалённых данных    | Soft Delete            |

---

# ⚠️ Важное замечание

Производительность Oracle нельзя оценивать только по названию технологии.

`Partitioning`, `Skip Scan`, `Result Cache`, `Reverse Key Index` и другие механизмы имеют свои ограничения и подходят для определённых сценариев.

Перед применением в production необходимо анализировать:

* объём и распределение данных;
* кардинальность;
* планы выполнения;
* характер нагрузки;
* конкуренцию транзакций;
* стоимость обслуживания индексов;
* версии Oracle;
* реальные метрики системы.

Поэтому примеры из репозитория лучше воспринимать как **лабораторные сценарии для изучения и экспериментов**, а не как универсальные рецепты оптимизации.
